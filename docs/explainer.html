1무엇을 하는 프로그램인가

KOSPI200 선물을 자동으로 사고파는 프로그램입니다. 매매 로직은 단순하고, 이 프로젝트의 핵심은 여러 스레드와 프로세스가 안전하게 협력하는 구조입니다.

매매 전략: N봉 고가 돌파 (롱 온리)

  • 시세를 받아 봉(bar)을 만든다. 모의 모드는 1초 봉, 실거래는 1분 봉
  • 현재가가 최근 N개 봉의 최고가를 넘으면 매수한다. 전략 8개가 각각 N=3, 5, 8, 4, 6, 10, 7, 12를 쓴다
  • 진입가 대비 손절(−0.15%, 실거래 −0.5%) 또는 익절(+0.25%, 실거래 +1.0%)에 도달하면 매도한다
  • 장 마감 시각(모의: 종료 6초 전, 실거래: 15:30)이 되면 전량 청산한다

3주문 한 건의 여정

시세 하나가 들어와서 매수 체결이 전략에게 전달되기까지를 단계별로 따라갑니다. "다음"을 누르면 구조도에서 해당 부분이 강조됩니다.

4세마포 기초 (이 프로젝트에서 쓰는 만큼만)

P와 V

세마포는 0 이상의 정수 하나와 대기열입니다.

  • P (wait): 값이 0보다 크면 1 빼고 통과하고, 0이면 잠든다
  • V (post): 값을 1 더하고, 잠든 스레드가 있으면 하나 깨운다
  • trywait: P와 같지만 0이면 잠들지 않고 실패를 돌려준다

POSIX는 sem_post가 그 값을 얻은 sem_wait보다 먼저 일어난 것(happens-before)으로 보장합니다. 그래서 V 전에 쓴 데이터는 P 이후에 안전하게 읽힙니다.

두 가지 쓰임새

카운팅개수가 있는 자원을 셉니다. 빈 칸 수, 1초 안에 쓸 수 있는 요청 수, 계좌 한도 계약 수, 미체결 주문 수 같은 것입니다. 이 프로젝트에서 세마포가 빛나는 곳이 여기입니다.

이진초기값 1이면 mutex처럼 씁니다. 이 프로젝트는 mutex도 이진 세마포로 통일했습니다. 동기화를 하나의 모델(P/V)로 논증하기 위해서입니다.

namedsem_open("/이름")으로 만들면 다른 프로세스도 이름으로 열 수 있습니다.

왜 전부 sem_open인가 — macOS는 이름 없는 세마포(sem_init)를 지원하지 않습니다(호출하면 ENOSYS). 그래서 이렇게 썼습니다.
  • 프로세스 내부용: 고유 이름으로 만들고 곧바로 sem_unlink합니다. 이름은 사라지고 핸들만 남아 익명 세마포처럼 동작하고, 프로그램이 비정상 종료해도 커널에 찌꺼기가 남지 않습니다. (src/sem.c isem_init_private)
  • 프로세스 간: 엔진이 이름으로 만들고, feeder는 같은 이름으로 엽니다. 이름은 엔진이 종료할 때 지웁니다.

5세마포를 어디에, 왜 썼나

각 카드는 "어떤 문제가 있었고, 세마포로 어떻게 풀었고, 없으면 무슨 일이 생기는가" 순서입니다.

① 유한 버퍼 — 생산자·소비자 카운팅이진

위치
src/bbuf.c · 주문 큐(order_q), 거래소 큐, 우편함의 큐 3개, 프로세스 간 시세 링
문제
전략 8개가 주문을 넣고 워커 4개가 꺼냅니다. 큐가 가득 차면 넣는 쪽이, 비면 꺼내는 쪽이 바쁜 대기(busy-wait) 없이 잠들어야 하고, 같은 칸을 두 스레드가 동시에 건드리면 안 됩니다.
해법
empty(빈 칸 수, 초기값=용량), full(찬 칸 수, 0), 생산자용 pmtx와 소비자용 cmtx(각 1)를 둡니다.
put:  P(empty); P(pmtx); slot[tail] = x; tail++; V(pmtx); V(full);
get:  P(full);  P(cmtx); x = slot[head]; head++; V(cmtx); V(empty);
핵심 1
P(empty)를 mutex보다 먼저. 순서를 바꾸면 버퍼가 꽉 찼을 때 생산자가 mutex를 쥔 채 잠듭니다. 그러면 다른 생산자는 mutex에서 막히고, 소비자가 칸을 비워도 그 생산자를 깨울 수 없습니다(교착). §6에서 직접 재현해 볼 수 있습니다.
핵심 2
생산자 mutex와 소비자 mutex를 분리. 생산자는 tail만, 소비자는 head만 건드리고, 같은 칸에 동시에 접근하지 않는다는 건 empty/full 카운트가 보장합니다. 그래서 넣기와 빼기가 병렬로 진행됩니다.
검증
test_bbuf: 생산자 16 × 소비자 4, 용량 1까지 → 유실 0, 중복 0, 끝난 뒤 permit 보존(empty=용량, full=0)

② 전략 우편함 — 큐 3개를 세마포 하나로 기다리기 카운팅

위치
src/inbox.c
문제
전략은 ① 내 주문의 체결/거절(ACK) ② 시계 틱·전량청산·종료(CTL) ③ 시세(MD) 중 아무거나 하나라도 오면 깨어나야 하고, 꺼낼 때는 ACK를 먼저 처리해야 합니다. 체결을 반영하기 전에 새 시세로 판단하면 이미 들어간 포지션을 모른 채 중복 진입할 수 있기 때문입니다.
해법
세 큐의 원소 총수를 세는 카운팅 세마포 items를 하나 더 둡니다.
// 생산자 (누구든)
bbuf_put(q_x, ev);  V(items);          // 넣은 다음에 알린다
// 소비자 (전략 스레드 1개)
P(items);
if (tryget(ack)) …  else if (tryget(ctl)) …  else tryget(md);   // 반드시 하나는 성공
왜 맞나
생산자는 넣기를 끝낸 뒤 V를 하고, 소비자는 하나뿐입니다. 그래서 P(items)가 통과하면 적어도 한 큐에 원소가 있고, 다른 누가 가져갈 수도 없습니다. 셋 다 실패하면 가정이 깨진 것이니 즉시 abort 합니다(실행 중 0회).
시세 버리기
시세 큐는 꽉 차면 tryput이 실패하고 버린 수를 셉니다. 느린 전략 때문에 md_receiver가 막혀서 다른 전략까지 시세를 못 받는 일을 막습니다. ACK는 절대 버리지 않습니다(⑥).

③ 포지션 장부 — 쓰기 스레드가 굶지 않는 Readers-Writers 락 이진 ×3

위치
src/rwlock.c, src/book.c
문제
장부는 상태 모니터, 전량청산 확인, 결과 검증이 자주 읽고, 체결 반영과 잔고 폴러만 가끔 씁니다. 읽기끼리는 동시에 해도 되지만, 단순한 "첫 reader가 잠그고 마지막 reader가 푼다" 방식은 reader가 끊임없이 오면 writer(체결 반영)가 영원히 못 들어갑니다.
해법
Downey, The Little Book of Semaphores §4.2.6 "No-starve readers-writers". 회전문 turnstile을 둡니다.
reader:  P(turnstile); V(turnstile);                 // 회전문을 통과만 한다
         P(rmtx); if (++readers == 1) P(room_empty); V(rmtx);
         … 읽기 …
         P(rmtx); if (--readers == 0) V(room_empty); V(rmtx);
writer:  P(turnstile);                                // 새 reader 유입 차단
         P(room_empty);  … 쓰기 …  V(turnstile); V(room_empty);
검증
test_rwlock: reader 8개가 쉬지 않는 중에도 writer 1만 회 이상 진입, 최대 대기 약 0.1ms, 상호배제 위반 0, 찢어진 읽기 0, reader 동시 진입 최대 8명

④ 레이트 리미터 — "1초에 최대 C건"을 증명 가능하게 카운팅named

위치
src/ratelimit.c · 시세용 rl_md(8/s, feeder 프로세스와 공유), 주문/잔고용 rl_trade(10/s)
문제
KIS는 초당 요청 수를 넘기면 EGW00201로 거절합니다.
해법
permit C개짜리 카운팅 세마포를 둡니다. 요청 전에 P 하고, 응답을 받은 시각 + 1초(+50ms 여유)가 지나면 refill 스레드가 V 합니다.
보장
같은 permit을 쓰는 연속된 두 요청은 다음 시작 ≥ 이전 응답 + 1초 ≥ 이전 서버 도착 + 1초를 만족합니다. 그래서 서버가 보는 어떤 1초 구간에도 permit 하나당 1건, 전체로는 최대 C건입니다. 흔한 "1초마다 C개 채워주기" 방식은 경계에서 순간적으로 2C건이 몰릴 수 있습니다.
예산 분할
시세(8/s)와 주문(10/s)의 permit을 따로 둡니다(합 18 < 서버 20). 하나를 같이 쓰면 시세 폴링이 permit을 다 써버려서 정작 중요한 주문이 굶습니다.
실측
같은 60초 조건에서 ON: EGW00201 0건 / OFF: 주문 303건 중 153건 거절, 서버 거절 합계 278건. OFF에서는 거절당한 전략이 매 틱마다 다시 시도하면서 요청이 불어납니다(재시도 폭주).

⑤ 계좌 한도 exposure — 읽고 판단하지 말고 "예약"하라 카운팅 (초기값 3)

위치
src/strategy.c try_entry
문제
"계좌 전체 롱은 3계약까지"라는 한도가 있습니다. 전략 A와 B가 동시에 장부를 읽고 "지금 2계약 < 3, 진입 가능"이라고 판단하면 둘 다 진입해서 4계약이 됩니다. 확인과 실행 사이에 상태가 바뀌는 TOCTOU 경쟁입니다. RW 락으로 장부를 읽는 것만으로는 막을 수 없습니다.
해법
진입 직전에 trywait(exposure) 합니다. "남았는지 확인 + 하나 차감"이 원자적이라 둘이 동시에 마지막 한 자리를 가져가는 일이 구조적으로 불가능합니다.
if (!trywait(exposure)) { risk_blocked++; return; }   // 자리가 없으면 진입 안 함
if (send_order(BUY)) holding++;
else V(exposure);                                       // 주문을 못 냈으면 자리 반납
// 진입 거절 ACK → V(exposure),  청산 체결 ACK → V(exposure)
검증
종료 후 permit 보존을 검사합니다: 남은 permit + 전략들이 쥔 permit = 3. 실행마다 "한도 때문에 진입 보류" 수백 회가 기록되는데, 한도는 한 번도 넘지 않았습니다.

⑥ 미체결 주문 한도 inflight — 교착이 없다는 증명의 열쇠 카운팅 (전략마다 K=2)

문제
워커와 거래소는 ACK를 전략 우편함에 넣습니다. ACK 큐가 꽉 차서 워커가 거기서 잠들면, 전략은 주문 큐에서 워커를 기다리고 워커는 ACK 큐에서 전략을 기다리는 순환 대기가 생길 수 있습니다. 게다가 워커는 registry 락을 쥔 채 ACK를 넣습니다(⑦).
해법
전략은 주문을 내기 전에 trywait(inflight) 하고, 그 주문의 최종 ACK(체결/거절)를 소비한 뒤에야 V 합니다.
증명
주문 하나는 ACK를 최대 2개(접수+체결, 또는 거절 1개) 만듭니다. 소비되지 않은 ACK가 남아 있는 주문은 permit을 쥐고 있으므로 K개 이하입니다. 따라서 큐에 쌓인 ACK ≤ 2K = 4 < 용량 64이고, ACK 넣기는 절대 막히지 않습니다. 그래서 tryput으로 구현했고, 실패하면 불변식 위반으로 abort 합니다(실행 중 0회). 이 성질은 전략 로직이 맞다는 가정 없이 세마포 하나만으로 성립합니다.

⑦ 주문 레지스트리 — "등록 전에 체결이 먼저 도착"하는 경쟁 이진

위치
src/registry.c
문제
체결 통보에는 브로커 주문번호(ODNO)만 있습니다. 거래소는 주문을 받는 즉시 처리를 시작하므로, 워커가 ODNO를 받아 표에 등록하기 전에 체결이 먼저 도착할 수 있습니다. 그냥 두면 체결이 주인을 못 찾고 사라집니다.
해법
주인을 못 찾은 체결은 버리지 않고 park(보관)합니다. 워커는 한 임계구역 안에서 ① 등록 ② 접수 ACK 전달 ③ park 목록 확인을 모두 합니다.
reg_bind (워커):   P(mtx); 등록; push(RECEIVED); park에서 내 체결 회수; V(mtx); 회수한 체결 전달
reg_route (거래소): P(mtx); 찾으면 → 엔트리 삭제 후 전달 / 못 찾으면 → park; V(mtx)
왜 맞나
두 동작이 같은 mtx로 직렬화되므로 순서는 둘 중 하나입니다. 거래소가 먼저면 park에 남고 워커가 봅니다. 워커가 먼저면 거래소가 엔트리를 찾습니다. 둘 다 서로를 못 보는 경우가 없습니다. 접수 ACK를 락 안에서 넣으므로 체결이 접수보다 먼저 전략에 도착하지도 않습니다.

7교착 상태가 생기지 않는 이유

교착 상태의 네 가지 조건(상호배제, 점유 대기, 비선점, 순환 대기) 중 하나만 깨면 됩니다. 이 엔진은 아래 세 가지 규칙으로 깹니다.

규칙 1. 이진 세마포(mutex)를 쥔 채 다른 것을 블로킹으로 기다리지 않는다

이진 세마포쥐고 있는 동안 하는 일
bbuf pmtx/cmtxmemcpy + 인덱스 증가
registry.mtx해시표 조작 + ACK 넣기(tryput, 규칙 2 때문에 절대 막히지 않음)
rwlock 내부, ledger, csv필드 몇 개 갱신 / 한 줄 쓰기

→ mutex에 대해서는 점유 대기 조건이 성립하지 않습니다.

규칙 2. 막힐 수 있는 put은 증명으로 없앤다

ACK 넣기는 ⑥ inflight 논증으로 공간이 항상 있습니다. 시세 넣기는 꽉 차면 버립니다. 그래서 전략 방향으로는 아무도 블로킹되지 않습니다.

규칙 3. 블로킹 대기는 한 방향으로만 흐른다

전략 ──(order_q 빈칸)──▶ 워커 ──(exch_q 빈칸)──▶ 거래소 ──▶ (블로킹 대기 없음)
                          └──(rl_trade permit)──▶ refill ──▶ (시간만 기다림)
md_receiver ──(md 링)──▶ feeder ──(rl_md permit)──▶ refill

화살표 끝의 스레드는 화살표 시작 쪽을 블로킹으로 기다리지 않습니다(워커와 거래소가 전략에게 보내는 것은 전부 tryput). 그래서 wait-for 그래프에 사이클이 없고, 순환 대기가 성립하지 않습니다.

종료할 때도 같은 원리입니다. feeder → md_receiver → nav/clock → 전략 → 워커 → 거래소 → refill 순서로 닫습니다. 각 단계에서 기다리는 쪽이 의존하는 상대는 아직 살아 있습니다. 예를 들어 워커가 rl_trade에서 잠들어 있어도 refill이 마지막까지 살아 있으므로 반드시 깨어납니다. 종료 신호(poison)는 소비자 수만큼 넣습니다. (src/engine.c 머리 주석)

8프로세스 분리와 장애 격리

fork가 아니라 posix_spawn

엔진은 이미 멀티스레드입니다. 이 상태에서 fork 하면 자식에게는 스레드 하나만 복제되는데, 다른 스레드가 쥐고 있던 락은 잠긴 채로 복사됩니다. 그 락을 풀어줄 스레드는 자식에게 없습니다.

그래서 posix_spawn(fork+exec)으로 새 프로그램을 시작하고, 자식은 핸들을 상속받는 대신 이름으로 shm_open, sem_open을 다시 엽니다. named 세마포가 꼭 필요한 이유가 이것입니다.

프로세스 간에는 mutex를 쓰지 않는다

이진 세마포를 쥔 프로세스가 kill -9 당하면 그 세마포는 영원히 0으로 남고, 상대 프로세스까지 멈춥니다. pthread의 robust mutex 같은 회복 장치가 세마포에는 없습니다.

  • 링은 SPSC라 mutex가 필요 없습니다. 카운팅 세마포는 생산자가 중간에 죽어도 "칸 하나가 줄어드는" 정도로만 손상됩니다
  • 레이트 리미터 반납 슬롯, 모의 서버 카운터는 lock-free CAS로 처리합니다
  • KIS 토큰은 이중 버퍼 + 버전 번호로 처리합니다(쓰는 쪽은 엔진 하나뿐)
장애 복구 실측 — 실행 중 feeder를 kill -9로 두 번 죽였습니다. 엔진의 main 스레드가 SIGCHLD로 감지하고, feeder가 쥐고 있던 permit을 회수한 뒤 다시 띄웠습니다(각각 약 4ms). 새 feeder는 이름으로 같은 링과 세마포에 다시 붙었고, 매매가 이어졌고, 불변식은 전부 통과했습니다. 반대로 엔진이 죽으면 feeder는 부모 pid가 바뀐 것을 보고 스스로 종료합니다.

9시그널과 종료

  1. 스레드를 하나도 만들기 전에 main이 SIGINT, SIGTERM, SIGALRM, SIGCHLD를 막습니다(pthread_sigmask). 이후 만든 스레드는 이 마스크를 물려받습니다.
  2. 그래서 시그널은 sigwait 중인 main에서만 동기적으로 처리됩니다. 세마포를 쥔 임의의 스레드가 비동기 시그널 핸들러에 끌려가는 일이 없습니다.
  3. SIGCHLD → feeder 재기동. SIGALRM(실행 시간 종료)이나 Ctrl+C → 종료 절차(§7) 시작.
  4. feeder에게는 막힌 마스크를 물려주지 않습니다(POSIX_SPAWN_SETSIGMASK). feeder는 Ctrl+C를 무시하고, SIGTERM 핸들러를 SA_RESTART 없이 답니다. 그래서 sem_wait에서 잠들어 있다가 EINTR로 깨어나 종료할 수 있습니다.

12예상 질문과 답변

시스템·병렬 프로그래밍 관점에서 나올 만한 질문들입니다.

왜 조건변수(pthread_cond) 대신 세마포를 썼나요?

이 시스템의 대기는 대부분 "개수가 있는 자원"입니다. 빈 칸 수, 초당 요청 수, 계좌 한도, 미체결 주문 수가 그렇습니다. 카운팅 세마포는 이 개수 자체를 상태로 들고 있어서 조건 검사와 대기가 한 연산에 들어 있고, spurious wakeup이나 lost wakeup을 따로 신경 쓸 필요가 없습니다. 예를 들어 V가 P보다 먼저 와도 값으로 남습니다. 또 named 세마포는 프로세스 간에 그대로 쓸 수 있습니다.

mutex 대신 이진 세마포를 쓰면 단점은 없나요?

있습니다. 세마포에는 소유자가 없어서 잘못된 스레드가 V를 해도 막아 주지 않고, 우선순위 상속과 robust 모드도 없습니다. 그래서 이진 세마포는 memcpy 수준의 짧은 임계구역에서만, 다른 대기 없이 쓰도록 제한했습니다. 프로세스 간에는 이진 세마포를 아예 쓰지 않았습니다(죽은 프로세스가 영원히 잠근 채 남는 문제 때문). 통일한 이유는 동기화 전체를 P/V 하나의 모델로 논증하기 위해서입니다.

유한 버퍼에서 P(empty)와 P(mutex) 순서를 바꾸면?

버퍼가 꽉 찼을 때 생산자가 mutex를 쥔 채 empty에서 잠듭니다. 소비자는 mutex를 못 얻어서 칸을 비울 수 없으니 교착입니다. 이 해설서 §6에서 재현할 수 있습니다. 참고로 이 구현은 생산자 mutex와 소비자 mutex가 분리돼 있어서, 순서를 바꿔도 생산자끼리만 막히고 소비자는 진행됩니다. 그래도 규칙대로 P(empty)를 먼저 합니다.

생산자와 소비자 mutex를 나눠도 안전한 근거는요?

① 읽히는 칸은 다 쓰인 칸입니다. 생산자 A가 칸 k를 쓰는 동안 pmtx를 쥐므로, 다음 생산자 B는 A가 다 쓴 뒤에야 칸 k+1을 받습니다. B가 먼저 V(full)을 해서 소비자가 칸 k를 읽더라도, A의 기록은 A의 V(pmtx) → B의 P(pmtx) → B의 V(full) → 소비자의 P(full) 순서로 happens-before가 이어져 있습니다. ② 쓰이는 칸은 다 읽힌 칸입니다. 읽기는 cmtx로 칸 순서대로 하나씩 일어나고, V(empty)는 읽기가 끝난 뒤에만 합니다. 그래서 n번째 생산자가 empty를 얻었다면, 덮어쓸 칸 n−cap은 이미 읽혔습니다.

Readers-Writers에서 writer 기아는 어떻게 막았나요?

회전문(turnstile) 세마포를 둡니다. reader는 회전문을 잡았다 바로 놓으며 통과만 하고, writer는 회전문을 쥔 채 room_empty를 기다립니다. writer가 회전문을 쥐는 순간 새 reader가 막히므로, writer는 이미 방 안에 있던 reader들만 기다리면 됩니다. 테스트에서 reader 8개가 쉬지 않는 중에도 writer 최대 대기가 약 0.1ms였습니다.

레이트 리미터가 정말로 1초 한도를 지킨다는 근거는요?

permit을 응답 받은 시각에서 1초 뒤에 돌려줍니다. 같은 permit을 쓰는 다음 요청의 시작은 이전 요청의 서버 도착보다 1초 이상 늦습니다(도착 ≤ 응답). 그래서 어떤 1초 구간에도 permit 하나당 요청은 최대 1건이고, permit이 C개뿐이니 최대 C건입니다. 테스트에서는 모든 요청 시작 시각을 기록해서 모든 슬라이딩 구간을 전수 검사했고, 프로세스 3개가 permit을 공유하는 경우도 검사했습니다.

멀티스레드로 실제로 무엇이 빨라졌나요?

병목은 CPU가 아니라 브로커 왕복(수십 ms)과 초당 한도입니다. 워커 여러 개가 I/O 대기를 겹치므로 주문 처리량이 늘어납니다(1→16개 15.2배). 반대로 전략 계산은 마이크로초 단위라서 전략 스레드를 나눈 목적은 속도가 아니라 격리입니다. 큐 하나의 처리량은 초당 40~70만 건에서 포화하는데, macOS named 세마포는 연산마다 커널 호출이고 큐 하나가 직렬화 지점이기 때문입니다. 이 시스템의 요구량(초당 수십 건)에는 충분합니다.

feeder를 왜 스레드가 아니라 프로세스로 뒀나요?

장애 격리와 재기동 때문입니다. 외부 네트워크와 라이브러리 쪽에서 크래시가 나도 포지션을 가진 엔진은 살아 있어야 합니다. 그리고 멀티스레드 상태에서 fork 하면 다른 스레드가 쥔 락이 잠긴 채 복제되므로, posix_spawn으로 새 프로그램을 띄우고 이름으로 세마포와 공유메모리에 다시 붙게 했습니다.

공유메모리에서 원자 변수(atomic)를 써도 되나요?

lock-free 원자 변수는 주소에 의존하지 않아서 서로 다른 프로세스가 같은 물리 메모리에 매핑해도 동작합니다. 시작할 때 atomic_is_lock_free로 확인합니다. 공유메모리에서 원자 변수는 통계 카운터와 CAS 슬롯(레이트 리미터 반납, 모의 서버)에만 쓰고, 대기는 전부 세마포로 합니다.

ThreadSanitizer 결과를 믿어도 되나요? 주석으로 숨긴 건 아닌가요?

주석은 세마포 래퍼 한 곳에만 있고, POSIX가 보장하는 sem_post → sem_wait 동기화를 그대로 표현합니다. 이게 버그를 가리지 않는다는 것을 확인하려고, 유한 버퍼에서 생산자 mutex 하나만 뺀 빌드를 만들었습니다. TSan이 즉시 data race를 보고합니다(make tsan-negative).

한계는 무엇인가요?

§13에 정리했습니다. 가장 큰 것은 실계좌 모드에서 KIS 실시간 체결 통보(WebSocket)를 연동하지 않아 접수 성공을 체결로 간주한다는 점입니다.
